# What Affects Vector Search Results

<Admonition type="note" title="">

* This article explains why vector search results might not always return what you expect, even when relevant documents exist.
  It applies to both [Dynamic vector search queries](../../ai-integration/vector-search/vector-search-using-dynamic-query.mdx) and
  [Static-index vector search queries](../../ai-integration/vector-search/vector-search-using-static-index.mdx).

* Vector search in RavenDB uses the [HNSW](https://en.wikipedia.org/wiki/Hierarchical_navigable_small_world) algorithm (Hierarchical Navigable Small World)
  to index and search high-dimensional vector embeddings efficiently.
  This algorithm prioritizes performance, speed, and scalability over exact precision.
  Due to its approximate nature, results may occasionally exclude some relevant documents.

* Several **indexing-time parameters** affect how the vector graph is built, and **query-time parameters** affect how the graph is searched.
  These settings influence the trade-off between speed and accuracy.

* RavenDB also provides [Exact vector search](#using-exact-search),  
  which finds the closest indexed vectors using exhaustive distance comparisons.

* In this article:
  * [The approximate nature of HNSW](#the-approximate-nature-of-hnsw)
  * [Indexing-time parameters](#indexing-time-parameters)
  * [Query-time parameters](#query-time-parameters)
  * [Using exact search](#using-exact-search)
    
</Admonition>

<Panel heading="The approximate nature of HNSW">

* **Graph structure**:  

  * HNSW builds a multi-layer graph, organizing vectors into a series of layers:  
    Top layers are sparse and support fast, broad navigation.  
    The bottom layer is dense and includes all indexed vectors for fine-grained matching.  
  * Each node (vector) is connected only to a limited number of neighbors, selected as the most relevant during indexing (graph build time).
    This limitation is controlled by the [Indexing-time parameters](#indexing-time-parameters) described below.
  * This structure speeds up search but increases the chance that a relevant vector is not visited during the search -  
    especially if it's poorly connected.

* **Insertion order effects**:  

  * Because the HNSW graph is append-only and built incrementally,  
    the order in which documents are inserted can affect the final graph structure.
  * Deleting a document removes its association with its indexed vectors.  
    A vector is soft-deleted only when no indexed documents reference it; its node remains in the graph.  
    Soft-deleted nodes are still traversed during search but are excluded from the results.
  * Updating a document can remove associations with old vectors and add associations with new ones.  
    Adding a vector that is not already in the graph creates a node and can change graph connections.  
    Adding a vector that is already in the graph, including a soft-deleted one, reuses its existing node.
  * This means that two databases containing the same documents may return different vector search results
    if the documents were inserted in a different order.

* **Parallel graph construction**:

  * To accelerate vector indexing, RavenDB can keep multiple HNSW placement operations in flight,
    batch the loading of vectors, and calculate distances in parallel.
  * Because in-flight vectors do not participate in graph construction exactly as they would in a strictly sequential build,
    the resulting graph is not guaranteed to be identical, even when the data and insertion order are the same.  
    Vector search results may therefore differ slightly.
  * To compensate, RavenDB adds edges from a vector being placed to other vectors whose placement is still in flight,
    allowing concurrently indexed vectors that would otherwise not consider one another during placement to become neighbors.
    These are regular graph edges: they can remain in the completed graph, although later edge filtering may remove them.
  * The results remain valid approximate nearest-neighbor results.  
    Greater build parallelism can improve indexing throughput at the cost of graph repeatability.
  * This behavior is controlled by the
    [Indexing.Corax.VectorSearch.MaximumConcurrentBatchesForHnswAcceleration](../../server/configuration/indexing-configuration.mdx#indexingcoraxvectorsearchmaximumconcurrentbatchesforhnswacceleration)
    configuration key. Server-wide and database values affect both static and auto indexes;
    static indexes can also override the setting per index.

* **Greedy search**:  

  * HNSW uses a greedy search strategy to perform approximate nearest-neighbor (ANN) searches:  
    Without a filter, the search starts at the top layer from an entry point.  
    It follows connections toward closer vectors in the upper layers, then explores a pool of candidates in the bottom layer.  
    When the vector search is combined with a filtering condition using AND, approximate search can instead start in the bottom layer, from nodes of documents that match the filter.
  * The algorithm doesn't exhaustively explore all possible paths, so it can miss the true global nearest neighbors -  
    especially if they are not well-connected in the graph.
    This design enables HNSW to find relevant results very quickly by focusing only on the most promising paths, making it highly efficient even for large datasets.
  * The search is influenced by the [Query-time params](#query-time-parameters) described below.  
    Slight variations in graph structure or search parameters can lead to different results.
  * While HNSW offers fast search performance at scale and quickly finds points that are likely to be among the nearest neighbors,
    it does not guarantee exact results - only approximate matches are returned.  
    This behavior is expected in all ANN algorithms, not just HNSW.  
    To find the closest indexed vectors through exhaustive comparison, consider using [Exact search](#using-exact-search).

</Panel>

<Panel heading="Indexing-time parameters">

The structure of the HNSW graph is determined at indexing time. 
RavenDB provides the following configuration parameters that control how the graph is built.
These parameters influence how vectors are connected and how effective the search will be.
They help keep memory usage and indexing time under control, but may also limit the graph’s ability to precisely represent all possible proximity relationships.

* **Number of edges**:  

  * This parameter, which corresponds to the _M_ parameter in the original [HNSW paper](https://arxiv.org/abs/1603.09320),  
    controls how many connections (edges) each vector maintains in the HNSW graph.  
    These edges define the structure of the graph and affect how vectors are reached during search.  
    When a node has too many edges, RavenDB prunes them, keeping a diverse set of close neighbors.  
    Starting from version 7.2.8, edge pruning uses a limit of _M_ neighbors in each upper layer and _2 × M_ in the bottom layer.
    In earlier versions, _M_ was used for all layers.  
    Connections added during parallel graph construction can cause a node to exceed these pruning limits.  
    Upgrading does not automatically rebuild existing graphs; later insertions can still change existing connections.  
    [Reset the index](../../client-api/operations/maintenance/indexes/reset-index.mdx) to rebuild the entire graph using the new edge limits.  
  * A **larger** number of edges increases the graph’s density, improving connectivity and typically resulting in more accurate search results, 
    but it may also increase memory usage, slow down index construction, and result in a larger index.  
    A **smaller** value reduces memory usage and speeds up indexing,  
    but can result in a sparser graph with weaker connectivity and reduced search accuracy.
  * With **static-indexes** -  
    This param can be set directly in the index definition. For example, see this [index definition](../../ai-integration/vector-search/vector-search-using-static-index.mdx#indexing-raw-text).  
    If not explicitly set, or when using **dynamic queries** -  
    the value is taken from the [Indexing.Corax.VectorSearch.DefaultNumberOfEdges](../../server/configuration/indexing-configuration.mdx#indexingcoraxvectorsearchdefaultnumberofedges) configuration key.  

* **Number of candidates at indexing time**:
   
  * During index construction, HNSW searches for potential neighbors when inserting each new vector into the graph.
    This parameter (commonly referred to as _efConstruction_) controls how many potential neighbors are kept in the candidate pool for each new vector.
    RavenDB may evaluate more vectors than this number while building the pool.
    HNSW selects graph connections from this pool, subject to the layer-specific edge limits described above.
  * A **larger** candidate pool increases the chance of finding better-connected neighbors, improving the overall accuracy of the graph.
    However, it may increase indexing time and memory usage.  
    A **smaller** value speeds up indexing and reduces resource usage,  
    but can result in a sparser and less accurate graph structure. 
  * With **static-indexes** -  
    This param can be set directly in the index definition. For example, see this [index definition](../../ai-integration/vector-search/vector-search-using-static-index.mdx#indexing-raw-text).  
    If not explicitly set, or when using **dynamic queries** - the value is taken from the  
    [Indexing.Corax.VectorSearch.DefaultNumberOfCandidatesForIndexing](../../server/configuration/indexing-configuration.mdx#indexingcoraxvectorsearchdefaultnumberofcandidatesforindexing) configuration key.

* **Build parallelism**:

  * The [Indexing.Corax.VectorSearch.MaximumConcurrentBatchesForHnswAcceleration](../../server/configuration/indexing-configuration.mdx#indexingcoraxvectorsearchmaximumconcurrentbatchesforhnswacceleration)
    configuration key controls the build parallelism described under
    [The approximate nature of HNSW](#the-approximate-nature-of-hnsw).
  * This is an index configuration setting, not a vector-field parameter.  
    It can be configured server-wide or per database, and static indexes can override it per index.

For the vector-field parameters described above, see
[Parameters defined in the index definition](../../ai-integration/vector-search/vector-search-using-static-index.mdx#parameters-defined-in-the-index-definition).

</Panel>

<Panel heading="Query-time parameters">

Once the index is built, the following query-time parameters influence the vector search - controlling how the HNSW graph is traversed and how results are selected.
These parameters directly affect how many results are found, how similar they are to the input vector, and how they are ranked.

* **Number of candidates at query time**:  
 
  * During approximate search, this parameter (commonly referred to as _efSearch_) controls the size of the retained pool of best-so-far candidate vectors.
    It influences the breadth of graph exploration; RavenDB can evaluate more vectors than the configured number.
  * In both approximate and exact search, it also limits the number of candidate vectors returned per query vector.  
    The number of resulting documents can be **lower** when several vectors belong to one document,
    or **higher** when the same vector is shared by several documents.  
    When the vector search is combined with a filtering condition using AND, only candidate vectors with at least one matching document count toward this limit.  
    Learn more in [How filtered vector search works](../../ai-integration/vector-search/more-querying-options.mdx#how-filtered-vector-search-works).
  * A **larger** value increases the breadth of the search, allowing the algorithm to explore a wider set of possible neighbors 
    and typically improving accuracy and the chances of retrieving all relevant results -  
    but this comes at the cost of slower query performance.  
    A **smaller** value speeds up queries and reduces resource usage -  
    but increases the chance of missing relevant results due to the more limited exploration.
  * This param can be set directly in the query. For example, see this [Query example](../../ai-integration/vector-search/vector-search-using-dynamic-query.mdx#querying-raw-text).
    If not explicitly set, the value is taken from the [Indexing.Corax.VectorSearch.DefaultNumberOfCandidatesForQuerying](../../server/configuration/indexing-configuration.mdx#indexingcoraxvectorsearchdefaultnumberofcandidatesforquerying) configuration key.  

* **Minimum similarity**:  
  
  * This parameter defines a minimum similarity on a normalized scale between `0.0` and `1.0`.
  * With `Single` or `Int8` embeddings, the normalized similarity is `(cosineSimilarity + 1) / 2`.  
    For example, a minimum similarity of `0.8` accepts cosine similarities of `0.6` or higher.  
    The threshold is therefore on a different scale from the cosine similarity used for vector scoring.
  * With `Binary` embeddings, the normalized similarity is the fraction of matching bits in the two vectors.
  * Candidates below the normalized threshold are excluded, even if they would otherwise be among the top candidates.
    Use this to filter out marginal matches, especially when minimum semantic relevance is important.
  * This param can be set directly in the query. For example, see this [Query example](../../ai-integration/vector-search/vector-search-using-dynamic-query.mdx#querying-raw-text).
    If not explicitly set in the query, the value is taken from the [Indexing.Corax.VectorSearch.DefaultMinimumSimilarity](../../server/configuration/indexing-configuration.mdx#indexingcoraxvectorsearchdefaultminimumsimilarity) configuration key.  
    The default value of this configuration key is `0.0`, which means no similarity filtering is applied - all candidates found during the search are eligible to be returned,
    regardless of how dissimilar they are from the query vector.

* **Search method**:  

  * You can choose between two vector search modes:  
    * **Approximate search** (default):  
      Uses the HNSW algorithm for fast, scalable search. While it doesn’t guarantee the absolute nearest vectors,  
      it is typically accurate and strongly recommended in most scenarios due to its performance.  
      When the vector search is combined with a filtering condition using AND, RavenDB may automatically switch to exact search over the documents that match the filter.  
      Learn more in [How filtered vector search works](../../ai-integration/vector-search/more-querying-options.mdx#how-filtered-vector-search-works).
    * **Exact search**:  
      Performs exhaustive distance comparisons against the relevant indexed vectors to find the closest matches.  
      Learn more in [Using exact search](#using-exact-search) below.

For all parameters that can be defined at query time, see:  
Dynamic queries - [The dynamic query parameters](../../ai-integration/vector-search/vector-search-using-dynamic-query.mdx#the-dynamic-query-parameters).  
Static index queries - [Parameters used at query time](../../ai-integration/vector-search/vector-search-using-static-index.mdx#parameters-used-at-query-time).   

</Panel>

<Panel heading="Using exact search">

* **When to use exact search**:  
  If you want to avoid the approximations of HNSW, you can use **exact search** instead.
  
* **How it works**:  
  Exact search compares the query vector with every indexed vector using the vector field's similarity function.  
  When the vector search is combined with a filtering condition using AND, RavenDB compares only the vectors of documents that match the filter.

* **Accuracy and quantization**:  
  Exact search finds the closest matches based on the vector representations stored in the index.  
  Quantization can change distances and rankings: exact search over `Int8` or `Binary` embeddings does not recover the original floating-point precision.
  Learn more in [Vector Search: Quantization](../../ai-integration/vector-search/quantization.mdx).

* **Query conditions**:  
  Minimum similarity, the number of candidates, and other query conditions still affect which results are returned.

* **Performance considerations**:  
  Scanning all relevant vectors is more resource-intensive and may be slower - especially for large indexes.  
  However, if the index is small, exact search can still offer reasonable performance.  
  Approximate search remains strongly recommended in most scenarios due to its performance.  
  Use exact search when exhaustive comparison is required and the performance trade-off is acceptable.

* **Supported queries and examples**:  
  Exact search can be used with both static index queries and dynamic queries.  
  For examples, see [Exact search](../../ai-integration/vector-search/more-querying-options.mdx#exact-search).

</Panel>
