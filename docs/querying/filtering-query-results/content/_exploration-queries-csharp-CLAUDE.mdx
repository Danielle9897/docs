<Admonition type="note" title="">

* An **exploration query** is a query that includes a `filter` clause.  
  The server applies `filter` to the results the query has already retrieved, before returning them to the client.

* The `filter` condition is **not evaluated against an index**, and **no index is created for it**.  
  The server scans the retrieved results one by one and evaluates the condition on each result using its JavaScript engine.

* You can add `filter` to each of the following query types:
    * **Full-collection query** -  
      The query retrieves all documents in the collection. No index is used.
    * **Dynamic query** -  
      A collection query that includes `where` or `order by`.  
      RavenDB uses (or creates) an auto-index for these clauses, but not for the `filter` condition.
    * **Static-index query** -  
      The query retrieves its results from the static index you specify.

* Exploration queries are intended for ad-hoc, one-time data exploration.  
  Since every retrieved result is scanned, filtering a large dataset is costly in server resources and query time.  
  [Limit the number of scanned results](../../../querying/filtering-query-results/exploration-queries.mdx#limit-the-number-of-scanned-results), 
  and use [where](../../../querying/filtering-query-results/filter-query-results.mdx) for queries you run repeatedly.

* The result counts in the examples below are based on the [sample data](../../../studio/database/tasks/create-sample-data.mdx).

<Panel heading="How exploration queries work">

* An exploration query is processed in the following order:

    1. **Retrieve**  
       The query retrieves its results from the collection or from an index (static or auto),  
       as defined by the `from`, `where`, and `order by` clauses.

    2. **Filter**  
       The server scans the retrieved results **in the order they were retrieved** and evaluates the `filter` condition on each one.  
       Results that match the condition are kept, results that don't match are skipped.  
       Scanning stops when one of the following occurs:
        * The requested number of results (page size) has been collected.  
          See [Filter and paging](../../../querying/filtering-query-results/exploration-queries.mdx#filter-and-paging).
        * All retrieved results have been scanned.
        * The number of scanned results has reached the `filter_limit`.  
          See [Limit the number of scanned results](../../../querying/filtering-query-results/exploration-queries.mdx#limit-the-number-of-scanned-results).

    3. **Project and return**  
       The results that passed the filter are projected (if the query has a `select` clause) and returned to the client.

* In RQL, the `filter` clause comes after `where`, `order by`, and `load`, and before `select`.  
  The `filter_limit` option is placed at the end of the query, together with `limit`:

    ```sql
    declare function ...         // Optional: a JavaScript function you can call from 'filter'
    from <collection | index>
    where ...                    // Optional: evaluated against the index
    order by ...                 // Optional: determines the order in which results are scanned
    load ...                     // Optional: load related documents to reference in 'filter'
    filter <condition>           // Evaluated on each retrieved result
    select ...                   // Optional: projection
    limit <offset>, <pageSize>   // Optional: paging
    filter_limit <number>        // Optional: the max number of results to scan
    ```

* **What the `filter` condition is evaluated against**:
    * **Full-collection queries and queries on a Map index** (static or auto):  
      The condition is evaluated against the **full document** stored in the database, not against the index entry.  
      You can reference any document field, including fields that are not indexed.
    * **Queries on a Map-Reduce index** (a static Map-Reduce index or a dynamic `group by` query):  
      The condition is evaluated against the **aggregation result**, so it references the reduce result fields.  
      See [Query a Map-Reduce index](../../../querying/filtering-query-results/exploration-queries.mdx#query-a-map-reduce-index).

* **Comparison semantics**:  
  The `filter` condition is translated to JavaScript, so comparisons follow JavaScript semantics:
    * `=` and `==` are evaluated as strict equality (`===`), and `!=` as strict inequality (`!==`).  
      Values are compared by both type and value.
    * String comparisons are **case-sensitive**.  
      For example, `filter Address.Country == "usa"` doesn't match a company whose country is `"USA"`.  
      This differs from `where`, where string comparisons are case-insensitive by default.

* **Query statistics**:  
  When a query includes `filter`, the [query statistics](../../../client-api/session/querying/how-to-get-query-statistics.mdx) report:
    * `ScannedResults` - the number of retrieved results that the filter scanned.
    * `SkippedResults` - includes the results that the filter rejected.

</Panel>

<Panel heading="When to use exploration queries">

* **Use `filter` when**:
    * You need a one-time look at your data, for example during development, debugging, or a support investigation,  
      and you don't want to create an index that the cluster would have to maintain from then on.
    * The condition references fields that are not indexed, and you don't want to add them to an index.
    * The condition can't be expressed with `where`, for example:
        * Comparing two fields of the same document - see [Filter with a JavaScript function](../../../querying/filtering-query-results/exploration-queries.mdx#filter-with-a-javascript-function).
        * Checking a field of a related document - see [Filter by a related document](../../../querying/filtering-query-results/exploration-queries.mdx#filter-by-a-related-document).

* **Prefer `where` when**:
    * The query runs repeatedly.  
      `where` is evaluated against an index. A dynamic query creates the required auto-index once,  
      and subsequent queries are served from it.
    * The query retrieves a large dataset.  
      `filter` scans every retrieved result each time the query runs, so its cost grows with the number of scanned results.

* If you do filter a large dataset:
    * Narrow down the retrieved results with `where` first, so fewer results are scanned.
    * Set a [filter_limit](../../../querying/filtering-query-results/exploration-queries.mdx#limit-the-number-of-scanned-results) to cap the number of scanned results.

* **`where` vs `filter`**:

    |                       | `where`                                                                   | `filter`                                                       |
    |-----------------------|---------------------------------------------------------------------------|----------------------------------------------------------------|
    | **Evaluated against** | Index entries (static index or auto-index)                                | Each retrieved result (document or aggregation result)         |
    | **Index usage**       | Uses an index.<br/>A dynamic query creates an auto-index when needed.     | No index is used or created for the `filter` condition.        |
    | **Cost per query**    | An index lookup                                                           | Grows with the number of scanned results                       |
    | **String comparison** | Case-insensitive by default                                               | Case-sensitive                                                 |
    | **Best for**          | Recurring queries                                                         | Ad-hoc exploration                                             |

</Panel>

<Panel heading="Exploration queries vs disabling auto-index creation">

* RavenDB provides two settings that prevent dynamic queries from creating auto-indexes.  
  The following table compares them with `filter`:

    |                                                                                                                                                                              | Scope                                                       | Effect                                                                                                                       |
    |------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------|
    | **Studio**: [Disable auto-index creation](../../../studio/database/settings/studio-configuration.mdx#disabling-auto-index-creation-on-studio-queries-or-patches)              | Queries and patches run from the Studio,<br/>per database   | A dynamic query fails if no matching auto-index exists.<br/>Existing auto-indexes are still used.                           |
    | **Configuration**: [Indexing.DisableQueryOptimizerGeneratedIndexes](../../../server/configuration/indexing-configuration.mdx#indexingdisablequeryoptimizergeneratedindexes) | Queries from all clients,<br/>server-wide or per database   | Dynamic queries are not supported.<br/>Full-collection queries and queries by document ID still work.                       |
    | **Query**: `filter`                                                                                                                                                          | A single query                                              | Filters the retrieved results without an index.<br/>No auto-index is created for the `filter` condition.                     |

* **The settings and `filter` address different needs**:
    * The settings **protect** the database from auto-indexes created as a side effect of ad-hoc queries.  
      They don't let you query by fields that no index covers - such a dynamic query fails.
    * `filter` **lets you query** by any field without an index, per query, with no configuration change.

* **A full-collection query with `filter` requires no index**,  
  so it works even when auto-index creation is disabled by either setting.  
  However, if the exploration query also includes `where` or `order by` on a collection, it is a dynamic query that requires an auto-index for these clauses,  
  and is subject to these settings like any other dynamic query.

* **The two complement each other**:  
  Disable auto-index creation to prevent accidental index creation,  
  and use `filter` to explore data that no index covers.

</Panel>

<Panel heading="Filter a dynamic query">

* When a collection query includes a `where` condition (other than on the document ID only), it is a dynamic query:  
  RavenDB evaluates the `where` condition against an auto-index, creating the auto-index if it doesn't exist yet.  
  Learn more in [Query a collection - with filtering](../../../querying/overview.mdx#2-query-a-collection---with-filtering).

* Adding `filter` to a dynamic query scans only the results that matched the `where` condition.  
  The fields referenced in `filter` are **not** added to the auto-index.

* The following query retrieves companies whose contact is a sales representative,  
  and then filters these results to companies located in Germany:

    // 'Filter' scans only the results that matched the 'Where' condition.
    // 'Address.Country' is NOT added to the auto-index.

<Panel heading="Filter a static-index query">

### Query a Map index

* When querying a static Map index, the `where` condition is evaluated against the index fields,  
  while the `filter` condition is evaluated against the full documents that the index query retrieved.  
  This lets you filter by document fields that the index doesn't include, without modifying the index.

* For example, the following index indexes the `Category` field of _Product_ documents:

<TabItem>
```csharp
public class Products_ByCategory : AbstractIndexCreationTask<Product>
{
    public class IndexEntry
    {
        // The index field
        public string Category { get; set; }
    }

    public Products_ByCategory()
    {
        Map = products => from product in products
                          select new IndexEntry
                          {
                              Category = product.Category
                          };
    }
}
```
</TabItem>

* The following query retrieves the beverages (_categories/1-A_) from the index,  
  and then filters these results to products priced above 20.  
  `PricePerUnit` is not an index field, but `filter` can reference it because it is evaluated against the document:

<Tabs groupId='languageSyntax'>
<TabItem value="Query" label="Query">
```csharp
List<Product> products = session
    .Query<Product, Products_ByCategory>()
    // 'Where' is evaluated against the index field 'Category'
    .Where(p => p.Category == "categories/1-A")
    // 'Filter' is evaluated against each retrieved Product document
    .Filter(p => p.PricePerUnit > 20)
    .ToList();
```
</TabItem>
<TabItem value="Query_async" label="Query_async">
```csharp

    .Query<Product, Products_ByCategory>()
    // 'Where' is evaluated against the index field 'Category'

    .Filter(p => p.PricePerUnit > 20)
    .ToListAsync();
```
</TabItem>

### Query a Map-Reduce index

* When querying a Map-Reduce index, the `filter` condition is evaluated against the **aggregation results**,  
  so it references the reduce result fields rather than the original documents.

* For example, the Map-Reduce index _Orders/ByCompany_ (included in the sample data) aggregates the number of orders per company in a `Count` field.  
  The following query returns the aggregation results of companies that placed more than 20 orders:

    ```sql
    from index "Orders/ByCompany"
    filter Count > 20
    ```

* Since all reduce result fields are indexed, a `where` clause (`where Count > 20`) returns the same results using the index.  
  Using `filter` on Map-Reduce results is mainly relevant in a **sharded database**,  
  where `filter` is executed on the orchestrator over the combined aggregation results of all shards.  
  Learn more in [Sharding: Filtering query results](../../../sharding/querying.mdx#filtering-query-results).

</Panel>

<Panel heading="Limit the number of scanned results">

* Use `filter_limit` (in RQL) or the `limit` parameter of `Filter` (in LINQ and DocumentQuery)  
  to set the **maximum number of retrieved results that the filter will scan**.

* `filter_limit` does **not** set the number of results the query returns.  
  The filter scans the retrieved results in order, and stops once it has scanned `filter_limit` results.  
  Results beyond the limit are not scanned, so they are not returned even if they match the condition.

* **For example**:  
  Assume a query retrieves the following results, in this order,  
  and applies `filter Country == "USA"` with `filter_limit 2`:

    | Retrieved result (in order) | Country  | Scanned by filter        | Returned |
    |-----------------------------|----------|--------------------------|----------|
    | Employee 1                  | USA      | ✅ Yes                   | ✅ Yes   |
    | Employee 2                  | Israel   | ✅ Yes                   | ❌ No    |
    | Employee 3                  | USA      | ❌ No (beyond the limit) | ❌ No    |

    Only _Employee 1_ and _Employee 2_ are scanned, so only _Employee 1_ is returned -  
    not 2 results, as one might expect from a limit of 2.

* **As a result**:
    * The number of returned results is at most `filter_limit`.
    * The query may return fewer results than exist, or no results at all, even when more matching results exist beyond the limit.
    * Which results are scanned depends on the order in which the query retrieves them.  
      To control this order, see [Filter and sorting](../../../querying/filtering-query-results/exploration-queries.mdx#filter-and-sorting).

* The following query scans only the first 100 orders in the _Orders_ collection,  
  and returns those shipped to the UK:

    * The filter scans only the first 100 retrieved orders, and returns the 4 orders among them that were shipped to the UK.

    * The limit must be greater than 0.
    * In a sharded database, the scan limit of a non-Map-Reduce query is applied by each shard to its own results.  
      Learn more in [Sharding: Filtering query results](../../../sharding/querying.mdx#filtering-query-results).

<Panel heading="Filter and paging">

* **Page size** (`Take` / the page size in `limit`):  
  Sets the maximum number of results that **pass the filter** and are returned.  
  The filter keeps scanning retrieved results until it collects a full page,  
  reaches the end of the retrieved results, or reaches the `filter_limit`.

* **Offset** (`Skip` / the offset in `limit`):  
  Sets how many **retrieved results** to skip before the filter starts scanning.  
  The offset is counted in retrieved results, **before** filtering, not in filtered results.

* **`filter_limit`** applies to each query execution separately,  
  so when paging, each page scans up to `filter_limit` results starting from its offset.

* **Paging through filtered results**:  
  Results that the filter rejected are counted in the `SkippedResults` query statistic.  
  To get the offset of the next page, add the number of results returned **and** `SkippedResults` to the current offset.  
  This is the same approach used when [paging through tampered results](../../../indexes/querying/paging.mdx#paging-through-tampered-results).

* **`TotalResults`**:  
  When a query includes `filter`, the `TotalResults` query statistic does not reflect the number of results that pass the filter.  
  Do not use it to calculate the number of pages - keep requesting pages until an empty page is returned.

* The following example pages through all orders shipped to the USA, 10 results per page:

<Tabs groupId='languageSyntax'>
<TabItem value="Query" label="Query">
```csharp
const int pageSize = 10;
int offset = 0;
List<Order> pagedResults;

do
{
    pagedResults = session
        .Query<Order>()
        .Statistics(out QueryStatistics stats)
        .Filter(o => o.ShipTo.Country == "USA")
        // Skip the retrieved results that were already scanned
        .Skip(offset)
        // Return at most 'pageSize' results that passed the filter
        .Take(pageSize)
        .ToList();

    // Process the current page here...

    // Advance the offset by the results returned AND the results the filter rejected
    offset += pagedResults.Count + (int)stats.SkippedResults;
}
while (pagedResults.Count > 0);
```

<Panel heading="Filter with a JavaScript function">

* In RQL, you can define a JavaScript function using the [declare](../../../querying/rql/what-is-rql.mdx#declare) keyword,

<Panel heading="Supported operators and limitations">

* **Supported in a `filter` condition (RQL)**:
    * Comparison operators: `=`, `==`, `!=`, `<>`, `<`, `<=`, `>`, `>=`
    * Logical operators: `and`, `or`, `not`, and parentheses for grouping  
      Note: a `filter` condition that **starts** with `not` doesn't return the expected results.  
      To negate a condition, precede `not` with `true and` (as LINQ and DocumentQuery do), or use `!=`.  
      For example: `filter true and not (Address.Country == "USA")`.
    * The `in` operator
    * The methods `startsWith()`, `endsWith()`, `regex()`, and `exists()`  
      Note: `startsWith()` and `endsWith()` compare strings case-insensitively, unlike `==`.
    * Fields of related documents loaded with [load](../../../querying/filtering-query-results/exploration-queries.mdx#filter-by-a-related-document)
    * JavaScript functions defined with [declare](../../../querying/filtering-query-results/exploration-queries.mdx#filter-with-a-javascript-function)

* **Supported in `Filter` (LINQ and DocumentQuery)**:
    * Comparison operators and logical operators only.  
      In DocumentQuery, use the `IFilterFactory` methods listed in [Syntax](../../../querying/filtering-query-results/exploration-queries.mdx#syntax).
    * Other query methods, such as `StartsWith`, `In`, `Search`, `ContainsAny`, or `ContainsAll`, are not supported inside `Filter` and throw an `InvalidQueryException`.  
      To use `in`, `startsWith()`, `endsWith()`, `regex()`, `load`, or a declared function, write the query in RQL and run it using `RawQuery`.
    * In LINQ, calling `Filter` more than once combines the conditions with `and`.

* **Not supported**:
    * **Faceted search**:  
      A [faceted search](../../../indexes/querying/faceted-search.mdx) query that includes `filter` throws an `InvalidQueryException`.
    * **Index-based query methods**:  
      `search()`, `boost()`, `lucene()`, `exact()`, `moreLikeThis()`, spatial methods, and vector search can't be used in a `filter` condition.  
      In addition, a query whose `where` clause contains `vector.search()` can't include `filter`.
    * **`between`**:  
      `between` is not supported in a `filter` condition. Use `>=` and `<=` instead,  
      e.g. `filter PricePerUnit >= 10 and PricePerUnit <= 20`.
    * **`now()` and `today()`**:  
      These functions can't be used in a `filter` condition.  
      Learn more in [Filter by date and time: Restrictions](../../../querying/filtering-query-results/filter-by-date-and-time.mdx#restrictions).
    * **Patch by query and delete by query**:  
      The query of a [patch by query](../../../documents/patching-documents/patch-multiple-documents/client-api.mdx) 
      or [delete by query](../../../client-api/operations/common/delete-by-query.mdx) operation can't include `filter`.  
      Use `where` instead.

</Panel>

| **limit**            | `int`                               | The maximum number of retrieved results that the filter scans.<br/>This is **not** the maximum number of results returned.<br/>Must be greater than 0.<br/>Default: `int.MaxValue` (scan all retrieved results).<br/>Translates to `filter_limit` in RQL. |
| **fieldName**        | `string`                            | The name of the field to compare. Use a dotted path for nested fields, e.g. `"Address.Country"`.                                                                                                                                      |
| **propertySelector** | `Expression<Func<T, object>>`       | A lambda expression selecting the field to compare.                                                                                                                                                                                 |
| **value**            | `object` / `TValue`                 | The value to compare against.                                                                                                                                                                                                       |
